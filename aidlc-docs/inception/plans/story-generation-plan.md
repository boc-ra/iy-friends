## 1. 目的
要件定義書（`aidlc-docs/inception/requirements/requirements.md`）の機能要件を、ペルソナごとの
ユーザーストーリー（INVEST 準拠）と受け入れ基準（Acceptance Criteria）に落とし込む。

## 2. 想定ペルソナ（初期案）
| ペルソナ | 説明 |
|---|---|
| 保護者・一般閲覧者（Viewer） | ログイン不要でチーム情報・ブログ・お知らせ・カレンダー・募集・問い合わせを利用 |
| 入部検討者（外部）（Prospect） | 入部を検討する保護者。募集案内・問い合わせが主目的 |
| 管理者（Admin） | 運営責任者。コンテンツ投稿＋編集者アカウント発行＋問い合わせ管理 |
| コーチ・スタッフ（Editor） | ブログ・お知らせを投稿。管理者の招待で参加 |

## 4. ストーリー分割アプローチ（選択肢）
- **A) ユーザージャーニー基準**: 利用者の一連の流れ（閲覧→問い合わせ、ログイン→投稿→公開）に沿って分割
- **B) 機能基準**: システム機能（ブログ、お知らせ、問い合わせ、認証…）ごとに分割
- **C) ペルソナ基準**: 利用者タイプ（閲覧者/管理者/編集者）ごとにグルーピング
- **D) ドメイン基準**: 業務領域（公開/運営）ごとに分割
- **E) エピック基準**: 上位エピック配下にサブストーリーを階層化
- **ハイブリッド**: 例）エピック（機能）配下にペルソナ別ストーリー

> 推奨（AI提案）: **B（機能基準）＋ C（ペルソナ）のハイブリッド** — 機能ごとにエピックを立て、各エピック内でペルソナ別にストーリーを記述。小規模サイトで見通しがよく、受け入れ基準もまとめやすい。

# 確定方針（回答の反映）

| 項目 | 決定 |
|---|---|
| ストーリー分割 | **機能エピック × ペルソナのハイブリッド**（Q-S1=B,C）。機能ごとにエピックを立て、各エピック内でペルソナ別にストーリーを記述 |
| 受け入れ基準の形式 | **Given / When / Then**（Q-S2=A） |
| ストーリーの粒度 | **中くらい（1機能＝1ストーリー程度）**（Q-S3=B） |
| 優先度 | **MoSCoW**（Q-S4=A）。要件書の優先度と整合 |
| リリース段階 | **2段階リリース**（Q-S5=B）。**Phase 1＝公開サイト（閲覧中心＋お問い合わせ送信）**、**Phase 2＝管理CMS（ブログ/お知らせ投稿・問い合わせ履歴管理・編集者招待）** |
| カレンダー | **自前カレンダー**（Q-S6=A）。管理画面から予定を登録して表示 |
| ブログ構成 | **単一ブログに統合**（Q-S7=C）。名称は **「スタッフの声」**（旧「監督達の声」「各コーチから」を統合） |

## 段階リリースに伴う設計上の依存（重要・記録）
- Q-S5=B により **管理CMSは Phase 2**。一方、Q-S6=A の自前カレンダーと、ブログ/お知らせの投稿は
  いずれも **管理画面（Phase 2）** に依存する。
- したがって **Phase 1** では：
  - ブログ記事は **既存記事の移行データを表示**（新規投稿UIは Phase 2）
  - お知らせ・カレンダーは、Phase 1 では **移行/初期投入データの表示**にとどめ、
    **管理画面からの登録・更新は Phase 2** とする
  - お問い合わせは **送信＋メール通知**を Phase 1 で提供し、**管理画面での履歴管理は Phase 2**
- この段階分けをストーリーの優先度（MoSCoW）とペルソナ×エピックのマッピングに反映する。

> ※上記方針で Part 2（personas.md / stories.md 生成）に進みます。
